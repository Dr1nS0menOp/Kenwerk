# Wave FX10: a search that ran out of time after a large import, and a release budget in queries

Builder report. It covers what was looked at, changed and proven.

## What was looked at

Several waves saw `TestAnOldPageIsFoundBehindAWholeWindowOfNewerPages` (search, 2,100 pages) find nothing under `go test -race`, also run alone on an idle build VM, and pass without `-race`. `TestAWholeSpaceReleaseFitsItsBudget` failed under load at 8 to 10 pages a second against its floor of 10. The question was whether a time limit of the product is tripped by a slow machine, which would mean real searches come back empty, or whether only the tests assume a fast machine.

### The search test

- The failing answer was `{"results": [], "total": 0, "timed_out": true}` after 3.1 s: the search reached `statement_timeout` (3 s, `statementTime` in `internal/search/search.go`). The answer already says that it ran out of time (ORG-032, `TestASearchThatRunsOutOfTimeSaysSo`), so nothing was silent; the search itself was slow.
- With `auto_explain` on the test database (`log_analyze`, 150 ms), one statement took all of it: the step that goes past the window of the 2,000 newest pages and asks the index of words (`sqlOf.every` for `textTier`). It took 2.13 to 2.57 s in every run, and the rest of the search milliseconds.
- Its plan: a nested loop with `search_pages` outside, estimated at 1 row and actually 2,102, and the subquery of word hits inside. A subquery fenced with `OFFSET 0` is not computed once: as the inner side of a nested loop it is run again for each outer row. So the GIN index `search_documents_tsv_idx` ran 2,102 times, about 1.1 ms each.
- The estimate of 1 row comes from statistics taken while the space was small: the test inserts 2,100 pages at once, as an import does, and autovacuum has not analysed the tables yet. When it had (a second search in the same run), the same search took 57 ms.
- The race detector does not slow PostgreSQL. Without `-race` the test failed as well: one of two plain runs on the VM, at 3.1 s. Under `-race` the margin of 0.5 s to 0.9 s is lost more often, which is why it showed there first.

So the cause is in the product, not in the test: after a large import into a space, and until autovacuum analyses the tables, a search for a word that only older pages hold runs the index once per page of the space. With some thousands of pages that is past 3 s, and the person is told the search ran out of time.

### The release budget test

- The two floors on time (10 pages a second, the release screen within 2 s) depend on the machine: the run is bound by the database, at 15 to 16 pages a second on the build VM with and without `-race`, 27 on the development PC of wave PB2. A loaded VM takes it below 10.
- The queries of the run are the same on every run: 130,637 for 2,001 pages in 9 batches (65.3 a page), in four runs, with and without `-race`, and 63,918 for 981 pages in one transaction (65.2 a page). The release screen costs 9 queries at 5,001 pages.

## What changed

- `internal/search/words.go`: the word hits of that step are a `MATERIALIZED` common table expression instead of a subquery with `OFFSET 0`. It is computed once whatever the plan: a nested loop rescans the stored rows, not the index. It still keeps the hits apart from the rest, which is why the fence was there (the planner reading the words of every page instead, 200 ms).
- `internal/search/words_plan_test.go`, new: `TestTheIndexOfWordsIsAskedOnceWhateverTheStatistics` builds the same shape in a throw-away database (statistics that know only other spaces, then a space of 2,101 pages), runs the step under `EXPLAIN (ANALYZE, FORMAT JSON)` with the settings of a search, and requires the index of words to run exactly once, with stale statistics and after `ANALYZE`, and the old page to be found. It counts index runs, so it does not depend on the speed of the machine. Before the fix it failed (the step ran past 3 s); after it, it passes.
- `scripts/mutation-check.sh`: a mutation that makes the expression `NOT MATERIALIZED`, caught by that test. Inlined, the hits are no longer kept apart, and the plan does not use that index at all (0 runs), most likely checking the words row by row, the case the fence was for.
- `internal/app/publishing_budget_test.go`: every run now bounds the work, which does not depend on the machine: at most 66 queries a page for both runs (one query more for each page fails), and 9 queries for the release screen at 5,001 pages. The floors on time stay as they were and are checked with `KENWERK_LOAD_BUDGET` set, the switch the other load tests of `internal/app` already use; the times are logged on every run. No guard was removed: a slower plan for a query of the run is no longer caught on a loaded machine, but a run with more queries is, on any machine.

## Decisions

Recorded on the product owner's behalf; they may be overruled.

- **Decided:** fix the plan of the search, not its limit. Raising or scaling the 3 s would only move the point at which a larger space fails, and keep a statement that does a thousand times the work it needs.
- **Decided:** no change to what a search answers when it runs out of time: it already says so with `timed_out`, and returns no partial list. A partial list in this step would show newer pages while an older match is not yet known, which an audit could take as the whole answer.
- **Decided:** the time floors of the release test run only with `KENWERK_LOAD_BUDGET`, and query bounds run always. The run is bound by the database, so its rate says more about the machine than about the code.
- **Not chosen:** running `ANALYZE` after an import. It would help this one path and leave the plan fragile for any other quick growth of a space.
- **Open:** a release run sends 65 queries a page and reaches 15 to 27 pages a second, below the 50 of PUB-1105. That was known since wave PB2 (59 statements a page then) and is not changed here.
