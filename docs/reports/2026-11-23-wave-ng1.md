# Wave NG1: the nightly checks run to the end again

Builder report. It covers why the nightly CI job had not passed since 12 November 2026, what changed, and how each step was proven.

## Why the nightly job failed

The scheduled runs of `ci.yml` from 13 to 23 November all failed in the job `nightly`. The job logs need a login, so the causes come from the steps' timings and the annotations, which the API gives without one, and from running the steps on the build machine.

| Nights | Step that failed | Cause |
|---|---|---|
| 14, 15, 16, 17, 18, 19, 20, 22, 23 November | The Go mutation check | The runner ran out of disk. Every annotation of those runs is `No space left on device`, from the runner's own log or from `tar`. On the 16th and the 14th the runner died before it could report a step. The check had 765 mutations on 13 November, which took 2 hours 9 minutes; it has 1,495 now. Each mutation compiles its own variant of the code into Go's build cache, which nothing empties during a run, so the cache grew with every mutation until the disk was full, after 3 to 4 hours. |
| 21 November | Fuzzing, `FuzzFromMarkdown` | `context deadline exceeded` when the target's 60 seconds ran out. Wave FZ1 (22 November) made the Markdown writer find the fence around code in one pass and added a long run of backticks to the fuzz corpus; the nights since fuzzed without a failure. The message itself is a known race in Go's fuzz coordinator (golang/go#75804), not fixed in Go 1.26.11, which can fail a target that never failed. |
| 13 November | The restore drill, exit code 22, after 77 seconds | Not found. Exit code 22 is `curl -f` on an answer of 400 or more, so one of the drill's requests was refused early in the drill; the drill sent all output to `/dev/null`, so the run does not say which. It was the first night with the restore from the console (wave RS) and with the database settings checked after a restore; the drill was changed again that day (RV3b) and passed in every builder's run since. The drill of that commit was run again on the build machine and stopped at `docker compose up`, before any request, with Docker's network address pools all but used up by other projects on that machine (30 networks, one free), so it neither confirmed nor ruled out a cause. The drill now names the line where it stops and the status of a refused request, so a repeat can be read from the annotations. |
| every night | Stryker | It ran after the Go mutation check in the same job, so it never started; it has never completed in CI. |

Behind the disk, the full mutation check would not have passed either: 38 of its 1,495 mutations no longer applied to the code. Most of them change a query of pages or spaces, and those queries gained a parameter for the spaces of a token (spec 096); a few others follow code that moved (the scope check of a token, the address check of outward connections, the password of the PDF helper, the timeout of a sign-in provider, a form of the console). A builder runs only the mutations near a change, and the full run that would have shown them never got that far. One of the 38 was a chain of two replaces of which the second no longer matched, so it ran half applied: a weaker mutation than its line says, which nothing reported.

Four of the twelve fuzz targets were never fuzzed at night: `FuzzEvaluationIsTotalAndBounded`, `FuzzImportArchive`, `FuzzRewriteLeavesNoDraftID` and `FuzzValidateNeverAcceptsAWorkflowWithoutAWayToApproval`. Their seed inputs ran as ordinary tests.

## What changed

- **Four jobs instead of one.** `nightly-fuzz`, `nightly-mutation`, `nightly-stryker` and `nightly-restore-drill` run side by side, on the schedule and when the workflow is started by hand (`workflow_dispatch`, new). One that fails no longer keeps the others from running, and each has a time limit that fits it: 40, 150, 120 and 45 minutes.
- **The Go mutation check in six shares.** `MUTATION_SHARD=k/n` in `scripts/mutation-check.sh` runs every n-th mutation of the file from the k-th on, so the n shares together run each mutation exactly once. `nightly-mutation` is a matrix of six shares, each on its own runner with its own PostgreSQL. No mutation line changed or went away.
- **The 38 mutations that drifted** break the same rule again in the code as it is. Where a mutation takes out a call such as `perm_visible_pages($1, $4)`, its replacement still uses every parameter of the query with its type (`$4::uuid[]`), so the query runs and the test fails on the rule, not on a parameter PostgreSQL cannot place. Two old mutations ("quick search shows hidden files", "the bell counts rows about hidden pages") replaced a table with one that has no column `page_id`, so they failed on a broken query; they now keep the column.
- **A mutation applies whole or not at all.** `apply` fails when any text a `replace` or `replaceAll` looks for is not in the file, so a chain cannot run half applied. `MUTATION_APPLY_ONLY=1` checks every mutation that way without running a test (39 seconds for all 1,495), and the `web` job runs it on every change, so a change that leaves a mutation behind fails at once.
- **Room on the disk.** The script empties Go's build cache when the disk under it has less than `MUTATION_MIN_FREE_MB` free (4,096 by default): it waits for the mutations under way, runs `go clean -cache`, and goes on. If the disk is still short with the cache empty, it stops with exit code 2 rather than fail later at random. Each share's runner also removes toolchains the job never uses (.NET, Android, GHC, CodeQL) and saves no build cache at the end.
- **Every fuzz target.** `make fuzz` runs `scripts/fuzz.sh`, which holds the table of all twelve targets with their times (30 or 60 seconds; about nine minutes of fuzzing). The script fails when a fuzz target in the code is missing from its table. A target runs once more only when it failed with `context deadline exceeded`, named no failing input, and wrote nothing into its corpus: that is the Go race and nothing else. Any other failure, or the race twice, fails the run. `scripts/fuzz-test.sh` holds this with a stand-in for `go` and runs before the fuzzing in CI.
- **Failures readable without the log.** The fuzz, Stryker and restore drill steps turn their failures into annotations, as the mutation step already did. The restore drill names the line where it stopped (an `ERR` trap) and its requests name a refused status (`curl -S`), since nearly all of its output goes to `/dev/null`.
- `make mutation-web` takes `STRYKER_ARGS`, such as `--concurrency 2` on a shared machine.
- The comment that said nine mutations break frontend rules says 39.

## Decision

Recorded on the product owner's behalf; it may be overruled.

- **Decided:** a fuzz target that fails with only the Go race runs once more. Wave FZ1 chose no workaround and to wait for the Go release with the fix; that release is not out (Go 1.26.11 is the newest 1.26 release on 23 November), and until it is the race can fail any night at random, which would keep C1 from ever being met. The retry is narrow: a real failure writes its input and says so, and then the run fails at once. When the toolchain moves to a Go release with the fix, the retry can go.
- **Not chosen:** a count of executions instead of a time (`-fuzztime Nx`), for FZ1's reason: the time would depend on the machine.

## How it was proven

A nightly run cannot be started from a branch that is not pushed, so each step ran on the shared build machine as the CI job runs it, one at a time, in the development container or, for the restore drill, on the machine itself. That machine was loaded by other work throughout (a load of about 10 on 10 cores), so its times are upper bounds, not what a hosted runner takes.

| Step | What ran | Result | Time |
|---|---|---|---|
| Fuzzing | `make fuzz` on two cores | All twelve targets held. `FuzzHTMLImport` failed once with only `context deadline exceeded` and no input, the Go race, and held when run again: the retry did what it is for | 16 minutes |
| Fuzzing finds a bug | A copy of the code with a panic planted in the SCIM filter parser, `FUZZ_ONLY=FuzzParseFilter` | Failed in 2.4 seconds, kept the failing input in `testdata`, and said `FAILED` with the input's path | 18 seconds |
| The fuzz script | `scripts/fuzz-test.sh`: nine cases with a stand-in for `go` | All pass; each of the three conditions of a retry was taken out in turn, and a case failed each time | under a second |
| The restore drill | `bash scripts/restore-drill.sh` | Passed, every step. The first try stopped in step 5, because Docker on that machine had used up its network address pools on other projects' networks (`all predefined address pools have been fully subnetted`), not on anything of the drill; the drill named the line, 242. The second try, with this worktree's own containers down, passed | 17 minutes, of which 214 seconds from backup to restored |
| The drill finds a bug | A copy whose `restore.sh` leaves the files out | Failed at line 181, the check that the attachment came back, with the command in the message | 6 minutes |
| Stryker | `make mutation-web STRYKER_ARGS="--concurrency 2"` | 3,694 mutants, 72.5% over all files; every file at or above its floor, so the ratchet passed. Five files are above their floor; the floors were not raised | 192 minutes |
| Every mutation applies | `MUTATION_APPLY_ONLY=1`, all 1,495 and each of the six shares | All apply; the shares hold 250 and 5 × 249, 1,495 together. With the three search mutations put back as they were, it reports all three, the half-applied chain among them | 39 seconds |
| The 38 repaired mutations | Each with its own tests | All 38 caught, each by a test of the rule it breaks | 38 minutes |
| Room on the disk | Four SCIM mutations with `MUTATION_MIN_FREE_MB` just under the free room, so the cache is emptied during the run | The run emptied the cache, went on, and caught all four. With a floor no disk can meet, it emptied the cache once and stopped with exit code 2 | 12 minutes |
| Shares and limits | `MUTATION_SHARD` of `0/3`, `4/3`, `1/0` and `abc`, `MUTATION_MIN_FREE_MB=lots` | Each refused with exit code 2 and a message | seconds |
| Lint | shellcheck of the four changed scripts, actionlint of the workflow | Nothing new. shellcheck's remaining notes are the quoted mutation lines (SC2016) and the four known ones in `restore-drill.sh`; actionlint's are in the `release-dry-run` job, which this wave did not touch | |

The first share of the full mutation check was started too: of its first 20 mutations, 18 were caught, one was a drifted mutation (now repaired), and one, in `internal/permissions`, ran into its 30-minute limit, as that package's tests do on this loaded machine. A full run of all 1,495 there, at the two jobs the machine allows, would take about a day, so it was stopped; the full run is the first nightly run on hosted runners.

## After the rebase onto main of 24 November

Main gained 47 mutation lines meanwhile (waves MC4, HF1, SO1 and others), all kept: the script holds 1,542 mutations (1,486 Go, 44 frontend, 12 editing service), six shares of 257. `MUTATION_APPLY_ONLY=1` found one more that had drifted, "a stored choice of another module is not read": HF1 put `LoadEach` between `Load` and `Store` in `internal/settings/settings.go`, so its anchor moved to `// LoadEach`. After that all 1,542 apply. The workflow keeps main's newer action pins and FX13's artifact step; `docs/testing.md` names the four nightly jobs, the twelve fuzzed targets and the shares.

## Left open

- **The full mutation check on hosted runners** has not run yet. The six shares should each take about 45 minutes, judged from the 765 mutations that took 2 hours 9 minutes on one runner on 13 November; the limit is 150 minutes. Starting the workflow by hand after this lands shows it before the next night.
- **Stryker's time on a hosted runner** is not known: 37.5 minutes in the development container, 192 on the loaded build machine. The limit is 300 minutes. If it ever comes close, Stryker has to be split by files, with the ratchet reading the merged reports.
- **The restore drill of 13 November**: its cause was not found (see above). If it comes back, the annotations now name the line.
- `internal/permissions` under mutation, with its 30-minute limit, is slow on the loaded build machine; on hosted runners it passed every night up to 13 November.
