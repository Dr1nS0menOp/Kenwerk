# Wave GO1: Go 1.27 and Debian 13 under the app

Wave MC4b needs `authelia.com/provider/oauth2`, whose `go.mod` asks for Go 1.27.0, and the dependency review of 2026-11-24 had already asked for the move to Go 1.27 and to `static-debian13`. This wave moves the toolchain and the base images, and nothing else.

The newest Go release was checked against go.dev on 2026-11-24: `go1.27.4` (2026-11-10) is the newest stable release, and the newest of the 1.26 line is `go1.26.11`. Node 26 has been the active LTS line ("Lithium") since 26.13.0 on 2026-10-28; Node 22 is in maintenance. Each digest was read from the registry for its tag on 2026-11-24.

Left as they were, on purpose:

- **`collab`** stays on `node:22-slim` (Debian 12). Its move to a distroless Node image waits for the product owner. The image scans clean today (below), but Debian 12 now gets only LTS security support, so that decision should not wait long.
- **The development toolbox's Node** (`node:22-bookworm-slim` in `Dockerfile.dev`) and the CI jobs `web`, `nightly-mutation` and `nightly-stryker` stay on Node 22: they also run the tests of `collab`, which runs on Node 22. Only the jobs that build the shipped web assets moved to Node 26.
- **`postgres:16`** keeps its digest. Its image is already Debian 13 (checked: `PRETTY_NAME="Debian GNU/Linux 13 (trixie)"` for the pinned digest), so the backup image, built on it, is Debian 13 too. Its stage runs `apt-get upgrade` at build time, and it scans clean.
- **`debian:12`** in the `release-dry-run` job is a test that the `.deb` installs on Debian 12, a distribution people still run, not a runtime image.

## Go 1.27 against what Kenwerk relies on

From the Go 1.27 release notes, checked against the code:

- **crypto/tls.** Five GODEBUG settings are removed for good (`tlsunsafeekm`, `tlsrsakex`, `tls3des`, `tls10server`, `x509keypairleaf`); Kenwerk sets none of them, in `go.mod`, a `//go:debug` line or its configuration. `Config.Rand` is deprecated; Kenwerk does not set it. Defaults for versions and cipher suites did not change.
- **crypto/x509.** `SystemCertPool` reads `SSL_CERT_FILE` and `SSL_CERT_DIR` on Windows and macOS too; on Linux, where Kenwerk runs, it always did. `Name.String()` now prints unknown string attributes as text; Kenwerk does not print certificate names.
- **net/http.** A client's `Response.Body` is drained up to a limit on close, which helps connection reuse; `internal/outward` sets `DisableKeepAlives`, so nothing changes there. The server gets `MaxHeaderValueCount` with a default; no route of Kenwerk sends or expects many values of one header. HTTP/2 honours client priorities.
- **encoding/json** is now built on `encoding/json/v2`, with the same results but other error texts. No test or code of Kenwerk compares a JSON error text (searched), and the upgrade test below runs a Go 1.26 node and a Go 1.27 node side by side on stored and sent JSON.
- **compress/flate** writes other bytes than Go 1.26. Nothing compares compressed bytes with a stored copy; the reproducible build compares two builds by the same toolchain.
- **Runtime.** Tracebacks of a `go 1.27` module show `runtime/pprof` labels; Kenwerk sets none. `asynctimerchan` is gone; Kenwerk never set it.
- **Tools.** `go test` runs vet's `stdversion` check; vet's `printf` check flags `%w` of a pointer to an error type; `gofmt` aligns some columns differently; `go mod tidy` merges `require` blocks. All of these were run: `gofmt -l`, `go vet`, staticcheck 2026.2.2 (v0.8.2, which reads Go 1.27.2's export data), golangci-lint 2.15.0 with the ratchet, and `go mod tidy -diff` found nothing to change.
- **The standard `uuid` package** is new in 1.27; Kenwerk keeps `google/uuid` by decision, so nothing changed.

Nothing broke, so no code changed.

## The fuzzing race

Go's fuzz coordinator could report "context deadline exceeded" when a target's time ran out (golang/go#75804). The fix, CL 774140, landed on the main branch as `5a957dc` on 2026-07-23 for Go 1.28, and was picked onto the Go 1.27 release branch as `184ce1510b` on 2026-07-27, before Go 1.27.0. GitHub's compare of `go1.27.0...184ce1510b` says "behind": the fix is in every Go 1.27 release. (The report of wave FZ1 expected it on the Go 1.26 branch as well; no 1.26 release so far carries it.)

So the narrow retry in `scripts/fuzz.sh` should never fire again. It stays as a guard, and its comment now says that a `RETRIED` line in a nightly log means the race is back. `scripts/fuzz-test.sh` passes, and one real target (`FuzzParseQuery`, 30 seconds) held under Go 1.27.4.
