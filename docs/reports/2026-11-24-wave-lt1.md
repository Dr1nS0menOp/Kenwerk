# Wave LT1: a load smoke test on every push

The product owner decided on 2026-11-24 that a short k6 load test runs in CI on every push, and that the test of 5,000 people stays a manual run on the server. This wave adds the CI job `load-smoke`.

## What runs

`scripts/load/smoke.sh`, in the job `load-smoke` of `.github/workflows/ci.yml` (after `go`, on every push and pull request, with a `postgres:16` service pinned by digest, as the `upgrade` job has):

1. downloads k6 2.4.0 and refuses it unless the archive has the pinned sha256;
2. builds the binary from the checkout and starts it on a database of its own;
3. seeds a small organisation through the public API with `scripts/stress/seed.py` and its fixed random seed: 200 people, 10 teams and "All staff", 20 spaces, 1,993 pages with their versions (seed.py's plan rounds each space down from 2,000), 200 files and 500 labels. Any item that fails to seed fails the job;
4. waits for the outbox to empty, runs `ANALYZE`, and runs `scripts/load/smoke.js` for 150 seconds;
5. keeps k6's whole summary as the artifact `load-smoke-summary` for 7 days, and on a failure prints the server's last log lines.

The scenario uses the open model of blueprint 07.8 (`constant-arrival-rate`), one scenario per read, so each read has its own steady stream and a slow server cannot slow the test down: page view 6 a second, bell 6, quick search 4, search 1, page tree 1, feed 1. That is about 19 requests a second, a tenth of the model's 180. Each simulated person logs in once as one of the seeded people.

## Thresholds, and where each comes from

All are set in one place, at the top of `scripts/load/smoke.js`. Each p95 budget is the design target already named in the blueprint or the existing k6 scripts, not a new number; the reports measured far below each, which leaves room for a shared runner.

| Read | p95 budget | Source of the budget | Measured before | Measured here (p95, three runs) |
|---|---|---|---|---|
| Page view | 300 ms | Blueprint 01: pages under 300 ms at p95 | 109 ms with 20 people (stress test, 10 November); 19 to 31 ms at the model (`limits.md`) | 9.2 to 9.5 ms |
| Bell | 100 ms | The target of `scripts/load/reading.js` | 80 ms before its fix (10 November); 5.8 ms after (`limits.md`) | 8.6 to 8.7 ms |
| Quick search | 500 ms | The target of `scripts/stress/load.js` | Typing 32 ms at the model (`limits.md`) | 34.0 to 35.3 ms |
| Search | 500 ms | ARC-200, `reading.js` | 44 ms at the model, 52 ms on a rare word (`limits.md`) | 44.3 to 46.8 ms |
| Page tree | 500 ms | ARC-199, `reading.js` | 134 ms with 20 people (10 November); 17 to 36 ms for a space of 3,978 pages (`limits.md`) | 9.2 to 9.7 ms |
| Feed | 500 ms | `reading.js` | 1.4 s before spec 061 (10 November); 20 to 72 ms after (`limits.md`) | 15.4 to 16.3 ms |

Besides the budgets: `http_req_failed` under 1%; no server error at all (a counter of every 5xx answer, so a "busy" 503 fails too: at this rate it is a regression); no dropped iteration; checks above 99%; and each read must have made more than 60 a second's worth of requests, because a threshold on a read with no requests would pass without a word.

The budgets are absolute, not compared with the last `main` as OPS-112 proposes; that comparison needs a stored baseline and is left for later.

## Proof

Run the way CI runs it, in the development container on this PC (16 CPUs, PostgreSQL of `compose.dev.yaml`, which runs without fsync), one run at a time under the shared lock, in the wave's own Compose project, taken down afterwards. The build VM's slot b stayed busy for more than 30 minutes, so the runs moved to this PC as the gate rules allow.

- **Three runs on green code** (`green1` to `green3`, 14:13 to 14:23): all thresholds held each time. Seeding took 20 seconds; every read had 150 to 901 requests, 0.00% failed, no server error, no dropped iteration. The spread of p95 between runs was under 3 ms for every read. Two earlier trial runs showed the same picture; the first stopped at the seeding check, which then expected 2,000 pages where seed.py makes 1,993, and the check was changed to look for failed items instead.
- **A regression is caught**: a `time.Sleep(150 * time.Millisecond)` at the top of `handleNotificationCount` made the bell's p95 157.7 ms against its budget of 100 ms. k6 exited 99 with "thresholds on metrics 'http_req_duration{route:bell}' have been crossed", the job's error annotation, and the server log; every other read stayed as before. The sleep was then taken out, and the diff of `internal/` is empty.

A hosted runner has 4 CPUs, with the load tool beside the app and PostgreSQL, and PostgreSQL there writes with fsync. The smallest headroom above is search, at about 11 times its measured p95; a runner several times slower than this PC still passes. The first CI runs on GitHub are the proof on a hosted runner.

## k6 as a dependency

- **Pin**: version 2.4.0 (released 2026-11-12, the newest release), the official `k6-v2.4.0-linux-amd64.tar.gz`, sha256 `5a5ecf23529ccf93135bc7e5b0c1cd5126ecf5f2672e22eed1556a0ab74abb87`, as listed in the release's `k6-v2.4.0-checksums.txt` and in GitHub's digest of the asset. k6 publishes no signatures (Scorecard Signed-Releases 0), so the hash is the pin.
- **OpenSSF Scorecard** of `grafana/k6`, 2026-11-23: **7.7**. Maintained 10, Code-Review 10, Dangerous-Workflow 10, Binary-Artifacts 10, Security-Policy 10, Packaging 10, Pinned-Dependencies 9, Token-Permissions 8; CII-Best-Practices 0, Fuzzing 0, Signed-Releases 0. Grafana Labs maintains it; 32,000 stars, commits the same day, a release every month or so, and two release lines (2.x and 1.8.x).
- **The official action** `grafana/setup-k6-action` (v1.3.0 at commit `c47136d33d365efbeb9ae7266908b5dcf98cdece`) has **no Scorecard** and 22 stars. A script that downloads the release and checks its hash adds no action, and runs the same in CI, in the development container and on the VM, so the action is not used.
- **Others looked at**: Locust (MIT, Scorecard 6.6, maintained) would need Python packages installed on the runner; Gatling (Apache-2.0, 5.4) needs a JVM; vegeta (MIT, 3.6) and hey (Apache-2.0, 3.4) score Maintained 0. The stress scripts are already k6. k6 stays.
- **Licence**: AGPL-3.0. It runs unmodified as a separate program in CI and is never linked or shipped, which blueprint 02 allows for a copyleft tool, as for golangci-lint (GPL-3.0). Recorded in `docs/dependencies.md` and `docs/dependency-inventory.md` (row added by hand in the generator's format; `scripts/dependency-inventory.mjs` now finds the pin in `scripts/load/smoke.sh`).

## Checks

- shellcheck 0.11.0 on `scripts/load/smoke.sh`: no findings.
- actionlint 1.7.7 on `ci.yml`: no finding in the new job. It reports two shellcheck notes (SC2013, SC2015, both "info") in the step "the two runs are the same, byte for byte" of `release-dry-run`, which `main` has too; not changed here.
- No Go code changed, so `make lint` does not apply.

## Not proven

- A run on a GitHub hosted runner: the first push is that proof.
- Writes: the smoke test reads only. Saving, comments and uploads are in the manual stress test.
- Capacity: a tenth of the model on a small organisation says nothing about 5,000 people.
