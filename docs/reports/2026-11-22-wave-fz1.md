# Wave FZ1: the nightly fuzz run, and fences in Markdown export

Builder report. It covers what was looked at, changed and proven.

## What was looked at

- The nightly job `make fuzz` ended in `--- FAIL: FuzzFromMarkdown (61.03s)` with `context deadline exceeded`, after status lines that showed 0 executions per second for stretches of about ten seconds.
- `FuzzFromMarkdown` was run locally for 10 minutes and again for 5 minutes with `GODEBUG=fuzzdebug=1`, on two workers. Every stretch at 0 executions per second lines up with the minimisation of a newly interesting input (`minimizing took: 9.9s`, `29.9s`, `50.8s`). Minimisation runs for up to `-fuzzminimizetime`, 60 seconds by default, and the status line counts no executions meanwhile.
- Every entry of the generated corpus (1,069 entries) was timed through the whole fuzz body, reading, the document gate and writing Markdown back: the slowest took under a millisecond. A copy of the fuzz target that kept every input slower than half a second found none in 8 minutes.
- The failure itself is a known race in the Go fuzz coordinator: when `-fuzztime` runs out, the deadline can be seen before the fuzzing context is cancelled, and the run is reported as failed with `context deadline exceeded` although the target never failed ([golang/go#75804](https://go.dev/issue/75804)). Go 1.26.11, the toolchain in `go.mod`, does not have the fix; Go 1.27.4 and the Go 1.26 release branch do.
- Inputs built to be hard for a Markdown reader, at 16, 64 and 256 KiB each, timed through the same steps: long runs of `*`, `_`, `` ` ``, `[`, `]`, `(`, `<`, `|`, `&`, `\`, `#`, `~` and `:`, open links and images, raw HTML and comments, autolinks, entities, many link reference definitions and uses, nested and loose lists and quotes, task boxes, headings, tables with many rows or columns, fences and indented code, and blocks just under the limit of spec 025.
- How the Markdown writer picks the length of a fence around code.

## What changed

- `ToMarkdown` finds the longest run of backticks in one pass and makes the fence one longer, at least three for a code block. The Markdown written is the same as before, byte for byte. This covers code blocks and inline code; nothing else in the writer grows a fence.
- The fuzz corpus in `internal/document/testdata/fuzz/FuzzFromMarkdown` gains a code block holding 32 KiB of backticks, so the fuzzer starts from that shape.
- Two mutations in `scripts/mutation-check.sh`: the fence grows one backtick at a time again, and a code fence may be shorter than three backticks.

## How the tests prove it

- `TestLongRunsOfBackticksAreWrittenAsMarkdownInLinearTime`: 256 KiB of backticks in a code block and in inline code must be written within 2 seconds, with a fence exactly one longer than the run. It takes about 10 ms.
- `TestAFenceIsOneLongerThanTheLongestRunOfBackticks`: the exact fence for code without backticks, with short runs, with three, and with runs of several lengths apart, for code blocks and inline code. It holds for the code before and after this wave, which shows the output did not change.

## Decision: the Go race

Recorded on the product owner's behalf; it may be overruled.

- **Decided:** no workaround in the Makefile. When Go 1.26.12 is out, the `toolchain` line moves to it, which brings the fix from the release branch. Until then, a nightly fuzz failure that says only `context deadline exceeded`, with no failing input written to `testdata`, is that race and not a finding.
- **Not chosen:** a count of executions instead of a time (`-fuzztime 300000x`), the workaround named in the Go issue, because the time the job takes would then depend on the machine; moving to Go 1.27 for this alone, because a new minor version of the toolchain is a change of its own.
- **For later:** with `-fuzztime 60s` and minimisation allowed 60 seconds, one minimisation can take most of a target's time. A shorter `-fuzzminimizetime` would leave more time for fuzzing.

## Other parsers

Each fuzzer of `make fuzz`, and `FuzzImportArchive`, ran for 2 minutes on two workers with debug output. None failed, and the slowest single input of each stayed under a millisecond; their stretches at 0 executions per second are minimisation too. The CSV import of people reads with `encoding/csv` line by line and stops at 1,000 lines; it has no fuzzer and was read, not fuzzed.
