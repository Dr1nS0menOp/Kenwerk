# Report: wave HF1, the header and footer of the installation (spec 089)

## What was asked

Build the header and footer of blueprint 03 (ADM-147 to ADM-149) as an experimental part, off by default behind its own switch under Administration, Organising (ADR-043). The study and spec of 2026-11-16 lay on an unmerged branch; `main` moved a long way since, so the spec was first updated where it moved, with each decision marked as taken on the product owner's behalf, and a section "Through the API" that lists every route with its scope.

## What changed in the spec before building

The section "Since the study" of spec 089 says what `main` became, and D15 to D24 what that changed:

- the product is Kenwerk; SC1, SC2 and SC4 landed, so the registry entry, `SettingsSection`, `SaveReset` and the page's order exist;
- RV11 (spec 090) landed: the audit gap the study found, that a settings change kept only its new values, is closed on `main`, and every link mark already loses its title at the gate. The header and footer record their change in the same `settings.updated` event with `changes`, with the documents whole (D16), and need no title rule of their own (D20);
- MC2 gives every route a scope; the three routes are `content:read`, `admin:read` and `admin:write` (spec, "Through the API");
- spec 085 lets a token read the administration, so the admin read is open to an administrator's token with `admin:read` (D19); the save stays sensitive and session-only;
- a login that is too old answers `403 reauth_required`, not `401` (D15);
- the code sits in a new package `internal/headerfooter`, because the cached read must know whether the part is on and the features package sits above settings (D17);
- the band is drawn from the subset by React, not by a read-only editor (D24).

## What was built

- **The gate** (`internal/document/header_footer.go`): after `Normalize`, a check that holds paragraphs, words, line breaks and status marks with bold, italic, underline, named colours and links; links only `https` to an ASCII host without a user part, one mail address, or a path inside; no control or direction characters; 600 characters, 5 paragraphs, 5 links, 3 status marks and 8 KiB per field. Anything else is refused with a problem (`not_allowed`, `link_not_allowed`, `text_not_allowed`, `too_long`), never dropped: the first run caught that a document holding only an image was counted as empty and stored as nothing, which is now refused.
- **The service** (`internal/headerfooter`): the save checks administration itself, checks both fields before anything is stored, compares under a row lock, and stores, audits and enqueues in one transaction; an unchanged save writes nothing. Readers are answered from a copy per node of 30 seconds, read in one statement over `experimental` and `header_footer`, dropped at once by a save or a change of the experimental parts on the node.
- **Routes:** `GET /api/v1/header-footer`, `GET /api/v1/admin/header-footer`, `PUT /api/v1/admin/header-footer`; `header_footer` in the capabilities.
- **Browser:** the section under Look with two fields whose editor offers exactly the subset (bold, italic, underline, colour, status mark, link, alignment), a hint from the server's limits, Save and Reset changes, a notice that names the refused field, and who changed it last; the band above and below the text of pages and blog posts, a named region each, outside links with their host and the outward mark, printed with the page.
