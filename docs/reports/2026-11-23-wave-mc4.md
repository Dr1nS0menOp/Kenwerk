# Wave MC4: assistants over HTTP at `/mcp`, and a switch for assistants

Builder report for the third build wave of spec 096 (access through the Model Context Protocol).

## What was looked at

- Spec 096 in full, the reports and handoffs of waves MC2 and MC3, the router, its scope table and the checks of a credential (`internal/httpapi/router.go`, `scopes.go`, `credentials.go`, `middleware.go`, `server.go`), the catalogue of `internal/mcp` and its classification of routes (`reach.go`), the settings sections (`internal/settings`), and the sections of the administration in the web app.
- The Streamable HTTP handler of the official MCP Go SDK v1.8.0, already a dependency: its stateless mode, the check of `Mcp-Method` and `Mcp-Name` against the body (`-32020`), the narrowing of protocol revisions, and its own check of the `Host` header for local addresses.
- Three modules for the authorization server, each resolved in a module of its own on the build machine with the licence file of every module it brings into a binary: `ory/fosite` v0.49.0, `go-oauth2/oauth2` v4.6.0 and `zitadel/oidc` v3.53.0. The findings are in spec 096, "Study before wave MC4": fosite's core brings two MPL-2.0 modules, which the licence gate of blueprint 02 refuses for what ships. That decision is the product owner's (question 5), so the wave was split (D27): this wave builds what does not depend on it.

## What changed

- **`POST /mcp`** (`internal/httpapi/handlers_mcp.go`): the 43 tools of MC3 over Streamable HTTP, stateless and in JSON, for revisions 2026-07-28 and 2025-11-25. The server of each message is built from the token's scopes. A tool's request runs through the router in process, behind the query limit, the permission memo, read freshness and maintenance, with the message's principal, address, user agent and request id, so the API decides it exactly as over HTTP. `GET` and `DELETE /mcp` answer `405`.
- **What `/mcp` takes**: only `Authorization: Bearer` with a token made For an assistant (D28). The authentication middleware does not read the session cookie on that path. An `Origin` other than the instance's public address is refused (`origin_refused`); the cross-origin protection of the whole server refuses a foreign one before that.
- **The switch for assistants** (D30): a settings section `assistants` with `mode` on, read only or off, shown under Administration, Security, **Assistants**, with the address of `/mcp`. `assistantMayGoOn` in the router applies it to every credential of an assistant at the API and at `/mcp`; on a read-only instance `GET /api/v1/me/credential` tells such a token only its reading scopes, so `kenwerk mcp` and `/mcp` offer only read tools.
- **The approval class in the router** (D29): every credential of an assistant is refused the routes of the approval class with `403 approval_required`, from the same list `call_api` uses, until approvals arrive in MC5. Tokens of scripts are untouched.
- **Docs**: spec 096 (status, the study, D27 to D32, question 5, "Through the API", "Built in wave MC4", the build plan split into MC4 and MC4b, the product owner's test steps), `docs/operations/mcp.md` (connecting over HTTP, the reverse proxy, the switch, new refusals), `docs/api/README.md`, `docs/api/routes.txt` and `openapi.json` (three routes), blueprint 03 PLT-047, the changelog.

No migration and no new dependency.

## How the tests prove it

Written before the code, failure paths first, in `internal/app/mcp_http_test.go` against the real router and database:

- `/mcp` answers `401` with a `Bearer` challenge without a token; a signed-in browser without a token gets `401` too, so the cookie is never read; a foreign `Origin`, and an `Origin` that is the address reached but not the public address, get `403`; a token not made for an assistant gets `assistant_token_required`; `GET` and `DELETE` get `405`; a `Mcp-Method` header that differs from the body gets `400` with `-32020`.
- With assistants off, `/mcp` and the API refuse an assistant's token with `assistants_off`, and a script's token still reads. On a read-only instance a change refuses with `assistants_read_only`, a read passes, the credential route names no changing scope, and `/mcp` lists `get_page` but not `update_page`.
- Walking every route of the approval class: each is a real route; an assistant's token with every scope is refused (`approval_required`, or `session_only` where only a browser reaches the route); a script's token with every scope is never refused for approval.
- Through a real MCP client over HTTP: `get_page` reads a page of the token's space, marked as data, and finds nothing of another space; `call_api` does not make a token; `rename_page` changes a page and the audit names the assistant's token; no result through `/mcp` holds a Kenwerk secret, also not the connection's own token.
- The cost of a tool call through `/mcp` against its API call (below).

## Load

A message to `/mcp` reads the token as any request does (one indexed read, the use written at most once a minute), and one read of the settings section `assistants`; then exactly the budget of the route the tool runs. Every request of an assistant's token at the API also reads that section once, a single row by its key. `tools/list` reads nothing more. No new background work.
