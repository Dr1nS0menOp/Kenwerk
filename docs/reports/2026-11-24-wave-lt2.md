# Wave LT2: the load smoke test failed once on CI; the cause was a race in making roles

## What happened

The new CI job `load-smoke` (wave LT1) failed on its first hosted run (run 45422823626) and passed on the next (run 45437555924). The failed run never reached k6. While it seeded 200 people eight at a time, one `POST /api/v1/admin/users` answered 500, the script refused to measure a smaller organisation than it said, and the job ended with exit code 1. No read was slow, and no budget was crossed.

## The cause: two transactions made the same role

Each new person gets the default permissions one at a time, and each step asks `rbac_role_for` for the role that holds exactly that set. When no role holds it yet, the function made one, named with the next free number. On a new installation those sets have no role yet. Two transactions that asked at the same moment both found none and both picked the same name, and the second failed on the unique index `roles_name_key` (SQLSTATE 23505), which reached the API as an internal error. The 16-CPU machine of the LT1 proof runs never lost this race; the 4-CPU hosted runner did once in two runs.

People are created in parallel by scripts and by SCIM provisioning, and grants in spaces go through the same function, so this is a fault in the product, not in the test.

## The fix

Migration 0081 (expand, may run twice) replaces `rbac_role_for`. Finding an existing role is unchanged and takes no lock. Only when no role holds the set does the function take a transaction-level advisory lock for the scope, look again, and make the role only if it is still missing. A second transaction that needs the same set waits for the first to commit, then finds and takes its role. The lookup moved into `rbac_existing_role_for`, so both lookups are the same query.

- **Test first**: `internal/db/role_for_race_test.go`. One transaction makes the role and holds it uncommitted; a second asks for the same set and is seen waiting on a lock in `pg_stat_activity`; then the first commits. Without the migration the test failed with the CI's error, "duplicate key value violates unique constraint roles_name_key (SQLSTATE 23505)". With it, the second transaction gets the first's role and exactly one role holds the set. The test does not depend on timing: the first commits only once the second waits.
- **Mutation**: "SQL: two makers of one new role race" takes the lock out; the test catches it.

## The smoke test itself

- **Hosted-runner numbers** (run 45437555924, 4 CPUs, PostgreSQL with fsync), p95: page 15.4 ms, bell 12.0, quick search 42.0, search 52.2, tree 15.1, feed 20.1. The budgets (300, 100, 500, 500, 500, 500 ms) are 8 to 33 times those, so they stay as they were, with this run now named in the comment as their source.
- **An unmeasured warm-up of 15 seconds**: the first 15 seconds of each stream carry the route `warmup`, which no budget reads. In them each simulated person logs in, which is a deliberately slow password hash, and the caches fill. Errors there still count. The measured window stays 150 seconds.
- **A failure says why**: on any failure, not only k6's, the job prints the server's warnings and errors, and a seeding failure becomes an annotation with the request that failed. Before, the failed run showed only "exit code 1". seed.py's error lines went to standard error and were not kept; they are now.

## Proof

On this PC, in the development container (16 CPUs), under the shared lock, in the wave's own Compose project, taken down afterwards; rebased onto `main` at `74a5cbf` (Go 1.27):

- `go test ./internal/db/ ./internal/identity/`: pass.
- **Two green runs** of `scripts/load/smoke.sh`, with the warm-up: all thresholds held, 0.00% failed, no server error, no dropped iteration. p95 in ms, first and second run: page 9.0 and 9.2, bell 7.8 and 8.1, quick 31.1 and 33.9, search 33.7 and 40.1, tree 9.2 and 9.3, feed 14.1 and 13.3. Seeding took 16 to 20 seconds, with no failed item.
- **The regression is still caught**: with a 150 ms sleep at the top of `handleNotificationCount`, the bell's p95 was 157.4 ms against 100, k6 exited 99, and only `http_req_duration{route:bell}` was crossed. The sleep was taken out afterwards.
- The race test before the rebase: it failed without migration 0081 with SQLSTATE 23505 on `roles_name_key`, and passed with it.

## Not done

- `continue-on-error` was not needed: the job's one failure was this bug.
- `make check` and the full mutation run of the package were not repeated after the rebase onto Go 1.27 (the product owner asked to keep this wave small). On the base before the rebase, `internal/db` and `internal/identity` passed, `make lint` passed with the ratchet, and the mutation run of the changed files caught every mutation it reached, the new one included, before it was stopped for the rebase.
