# Wave QG2: eleven packages meet the quality limits

Builder report. Spec 097 holds the plan and, under "What QG2 cleaned", the outcome; this note holds what was tried and measured.

## Packages

Cleaned and taken off `scripts/lint-ratchet.txt`: `internal/mail`, `internal/outbox`, `internal/queue`, `internal/webui`, `internal/conditions`, `internal/people`, `internal/templates/fields`, `internal/sharing`, `internal/scim`, `internal/sites` and `internal/comments`. The list now names 25 packages.

Left for QG3: `internal/search` (6 findings), `internal/settings` (6) and `internal/sso` (5). Wave ST1 had uncommitted changes in `settings` and `sso` (and in `webui` and `mail/server.go`), and wave SR3 was working in `search`; cleaning them now would mostly have made merge conflicts.

## How the code was split

- Along steps the functions already had, one job each: checks before a change (`checkMayComment`, `checkMayAsk`, `editable`), the parts of a result (`files`, `htmlOptions`, `addThreads`), and the branches of a switch that had grown (`kindAnswer`, `pickedAnswer`, `patchGroup`, `patchMembers`).
- Errors stay the same values with the same words. In `scim`, a value that cannot be read became the sentinel `errBadValue`, which the handler answers with the same `400 invalidValue` as before; every other error still goes to `fail` unchanged.
- In `queue`, the embedded server starts in `startEmbedded`, which keeps the two error messages it had (`queue: create embedded NATS`, `queue: embedded NATS did not start`) and still returns before the connection is made.
- Long test functions became helpers (`enqueue`, `onlyMessage`, `waitForNothingWaiting`, `checkAnswer`, a `fakeSession` for the fake SMTP server), and the table of fillings in `templates/fields` became data at package level.

## Mutation lines

`scripts/mutation-check.sh` matches code as text, indentation included, and a changed script makes the targeted run run everything. So the split was planned around it: where a mutation names lines inside a closure (the loop of `Share`, "sharing gives access"; the check of the working version in `Create`; the `case` lines of the conditions), those lines stayed where they were, at the same depth. The script did not change.

## Tests first

Where the split code had no test of its own, the test came first:

- `webui`: which requests reach the app, how an asset, a file outside `assets/`, a missing asset, a route and a folder are answered, and an app without its frontend.
- `people`: every edge of a crop, no crop, a file of another format, and a header claiming 100,000 by 100,000 pixels with a correct checksum (the integration test accepts 400 or 413 there, because its header has a stale checksum; the new unit test pins 413).
- `sites`: the defaults and tidying of the input of a site, everything it refuses, and every accent and update mode it takes.
- `scim` (in `internal/app`): replacing members, removing one and all, a PATCH without a path, every value refused for a group and a user, and the membership check for a stranger, an unknown group and an id that is none. The integration tests covered only add, remove by path and rename before.

## gosec

Nine findings on six lines are values gosec cannot see are safe; each line carries `#nosec` with its reason. One more was fixed instead: the test of the pinned viewer files in `webui` reads them through `os.DirFS` and `fs.ReadFile`, which gosec does not flag and which reads the same files.

## Stryker

The spec gives QG2 the three files no unit test reached. `restriction-state.ts` got tests of its three states and the access row, `frame-messages.ts` of listening (only our frame on our origin, a frame that loads later, stopping) and sending (a named origin, `*` for an opaque one, no frame). Both run in Node: listening uses a stubbed `window` that is an `EventTarget`. `kept-fields.ts` needs a DOM (`HTMLInputElement`, `MutationObserver`, `sessionStorage`); the unit tests run without jsdom or happy-dom, and adding one is a new development package, so it is left for a decision. The floors in `scripts/stryker-ratchet.txt` were not raised: that needs a Stryker run, which is nightly; the next one may raise them.

## Measured

- The 1 ms budget of conditions (`TestEveryConditionOfAHundredEntryTemplateTakesUnderAMillisecond`) failed on the build VM, at about 1.1 to 1.35 ms. Measured in turns with main's `conditions.go` under the same load: 968, 1,043 and 1,000 µs against 970, 995 and 973 µs. Main fails there too; the VM was loaded by other waves. The test is skipped under the race detector, which is how `make check` runs the tests, so it does not run there.
- `internal/permissions` may time out on the loaded VM (known); see the gate results in the handoff.

## Gates run (build VM)

- `make check` with `TEST_SHARDS=2`: fmt-check, vet, staticcheck, govulncheck, `lint` (the ratchet: 25 packages listed, funlen 425, gocyclo 533, gosec 113, no package outside the list with a finding), secrets, audit, licences and web-check passed; under the race detector every package passed, `internal/app` in both shards, except `internal/permissions`, which timed out at 45 minutes on the loaded VM as it has before. This wave does not touch it. The first run had stopped at Prettier on the two new frontend tests, which were then formatted.
- Targeted mutation check (`MUTATION_CHANGED` with every changed file outside `internal/app`, `MUTATION_JOBS=2`): 106 of 1,476 mutations ran, all caught, none broken. `internal/app/scim_patch_test.go` was left out of the list on purpose: a changed file in `internal/app` selects every mutation whose tests run there; the mutations of `scim.go` run anyway, as `scim.go` is listed.
- Package tests, `go vet`, `gofmt` and golangci-lint of the eleven packages, the new SCIM and picture tests of `internal/app`, and `tsc`, ESLint, Prettier and Vitest on the new frontend tests.
