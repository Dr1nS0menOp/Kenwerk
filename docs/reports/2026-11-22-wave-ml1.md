# Report: wave ML1, the mail server in the administration (spec 098)

## What was asked

On 22 November 2026 the product owner said that Kenwerk is a product run from its screens and its API, and that the mail server, which could only be set in the environment, must be set in the administration too. The wave studies how mail is set today, plans and builds a section and its API with a test mail that says what the server answered, and sorts every other setting that is still environment-only for a later wave.

## Through the API

Spec 098 lists the routes. A token with the `admin` scope reads the server, never the password; changing it is a session's, as for all of the administration (spec 085).

## Decided on the product owner's behalf (may be overruled)

D1 to D11 in the spec. In short: the environment wins and locks the section; the password is sealed and never returned; every change is a system administrator's with a fresh login and a second factor; a stored server reaches only public addresses unless `KENWERK_OUTWARD_ALLOW_PRIVATE`; every node rereads within 5 seconds; the test sends at once with what is saved and replaces the test through the queue; encryption none takes no login; a table of its own; sender address and name apart, reply-to included; the audit keeps host, port, encryption, sender and reply-to, and redacts the user name and the password.

## Tests

- `internal/mail` (`server_test.go`): inside addresses refused unless allowed, every limit of the section, the step and the exact answer of the server for a refused sender, recipient, message and login, a stored server's dialer refusing this machine, the environment's sender with its name apart.
- `internal/app` (`mail_server_test.go`), against a local fake SMTP server: who may change it (member, administrator, token, no second factor, old login, then a system administrator); no read holds the password or its sealed form, through a session or a token; the password sealed, kept, removed, never in the audit, and never with encryption none; the environment locks it without spending the code; inside addresses refused when saving; a stored row whose address is inside refused when connecting; a change used without a restart on the saving node at once and on another node after its reread, also turning mail off; the test mail to the person who asks, the exact refusal, no row in the queue; the limit of 5 tests. `TestResealReachesTheMailServerPassword` and `TestEverySealedColumnIsKnown` for the key rotation.
- End to end: `admin-mail.spec.ts` (an administrator reads and cannot change; a system administrator saves with a code after a wrong one, Reset changes takes the code field away, the password is never shown; a locked server and a failed test, from routed answers). The test server keeps no mail server: what the spec saves leaves the host empty. `together`, `walk` and `health` follow the new words.
- Mutations: twelve lines under "Spec 098, wave ML1". The tests were split to keep every function within the lint limits of spec 097 (40 lines, complexity 10).

## What was not proven

- Delivery through a real provider with STARTTLS and a login: the tests use a fake server on this machine, with TLS and login in `internal/mail` and without TLS in `internal/app`.
- Two nodes in separate processes: the test runs a second app on the same database in one process.
